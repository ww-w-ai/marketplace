# better-rea

[English](./README.md) · 한국어

**실제 리버스엔지니어링 업계 수준의 보고 템플릿과 진짜 RE 엔지니어들의 방법론을 담아 — 당신이 RE 전문가가 아니어도 REA로 제대로 된 분석 결과를 뽑게 해주는 Claude Code 스킬.**

REA(Reverse Engineer Anything)는 에이전트를 실제 분석 엔진에 연결합니다 — 네이티브 바이너리에는 Ghidra, Electron·웹 앱에는 자바스크립트 분석. 그리고 결과를 증거와 한계를 단 형태로 돌려주고, 닿지 못한 것은 unknown으로 남깁니다. 여기까지는 REA가 하는 일입니다. 문제는 에이전트가 그걸 받아서 하는 행동이에요. 한 번 훑고 첫 답을 집은 다음 나머지를 그럴듯한 이야기로 메꿔버리는데, 그 결과는 그냥 모델한테 맡겼을 때와 결정적으로 다르지 않습니다. 진짜 리버스엔지니어가 더하는 건 또 다른 엔진이 아니라 — 끈질김, 보고 규율, 그리고 방법의 레퍼토리죠. `better-rea`는 그 세 가지를 에이전트에 쥐여주고, 없거나 반증된 주장을 인용한 보고서를 실패 처리하는 검증기 `scripts/check-ledger.mjs`를 함께 싣습니다.

아래 세 가지가 스킬이 REA 위에 더하는 것입니다. 테스트에서 결과를 끌어올린 건 이 셋이 함께 적용됐을 때였고, REA만 그냥 붙인 것은 모델에 맡긴 것을 결정적으로 넘지 못했습니다.

| 구성 | REA 위에 더하는 것 | 위치 |
|---|---|---|
| 루프 | 증거·한계·unknown은 REA가 이미 돌려준다. 루프는 그걸 받아서 멈추지 않는다 — 에이전트가 REA를 다시 돌리고 더 파서, 필요한 주장이 확인될 때까지 간다. 첫 그럴듯한 답에서 멈추지 않는다. | `references/loop.md` |
| 템플릿 | 실제 리버스엔지니어링 업계가 쓰는 수준의 보고 템플릿 — 관찰, 가설, 증거, 실제 메커니즘, 재현. 에이전트에 이 틀을 주는 것이 결과 수준을 끌어올렸다. | `assets/report-format.md` |
| 방법론 노트 | 실제로 일하는 RE 엔지니어들이 대상을 어떻게 공략하는지, 우리가 리서치해 거론한 수많은 방법론의 라이브러리. 하나의 정해진 절차가 아니라 에이전트가 꺼내 쓸 '가능성'으로 제공해, 한 방법에 갇히지 않게 한다. | `references/methods.md` |
| 강제 | 원장에 없거나 반증된 주장을 인용하면 검증기가 0이 아닌 코드로 종료한다. | `scripts/check-ledger.mjs` |

## REA만으로는 왜 부족한가

빌드된 앱만 있고 소스는 없습니다. REA를 붙인 에이전트에게 구조를 설명해 달라고 하면, 깔끔한 다이어그램과 이름 붙은 모듈, 기능이 어떻게 도는지에 대한 자신만만한 설명이 돌아옵니다.

그런데 확인해 보면 모듈 이름은 추측이고, 데이터 흐름은 '그런 류의 앱이 보통 하는 것'이지 '이 앱이 실제로 하는 것'이 아닙니다. 함수도, 주소도, 디스어셈블리 한 줄도 가리키지 않아요. 증거는 있었는데 — REA가 꺼내주니까 — 에이전트가 중간에 멈추고, 보고 규율도 어디를 볼지에 대한 방법도 없이 그 빈칸을 사실처럼 써버린 겁니다.

여러 구성으로 테스트해보니, REA를 그냥 붙이는 것만으로는 모델에 맡긴 것을 결정적으로 넘지 못했습니다. 리프트는 아래 세 가지에서, 그것도 셋이 함께 적용됐을 때만 났어요.

## better-rea가 더하는 것

**1. 한 번이 아니라 루프.** REA는 증거·한계·unknown을 스스로 돌려줍니다. 한 번에 두면 에이전트는 첫 답을 집어요. 스킬은 REA를 루프 안에서 돌립니다 — 모든 결론을 원장에 주장으로 적고, 필요한 주장이 확인될 때까지 분석을 다시 파고 돌립니다. 아니면 정직하게 unknown으로 남기고요. 끈질김이 핵심입니다.

**2. 업계 수준의 보고 템플릿.** 보고서는 원장에서, 실제 리버스엔지니어링 작업이 쓰는 형식으로 조립됩니다.

```text
관찰(Observed behavior)     밖에서 보이는 앱의 동작
가설(Hypotheses)            검토한 후보 설명 — 틀린 것까지
증거(Evidence)              위치를 단 원장 항목
실제 메커니즘(Actual)        결론 — 모든 문장이 '증거'의 한 줄로 이어진다
재현(Reproduce / verify)    다른 사람이 돌려 확인할 수 있는 절차
```

에이전트가 답을 자유형식으로 쓰게 두는 대신 이 템플릿을 주는 것이, 결과 수준을 끌어올린 지점입니다.

**3. 실제 RE 방법론을, 가능성으로.** 스킬은 실제로 일하는 리버스엔지니어들이 어떻게 움직이는지 — 메커니즘이 보통 어디에 사는지, 어떤 경로를 따라가는지, 무엇을 무엇과 대조해 확인하는지 — 우리가 리서치한 방법론의 라이브러리를 들고 있습니다. 하나의 강제된 절차가 아니라 에이전트가 꺼내 쓸 선택지로 주어져, 처음 걸린 방법이 아니라 맞는 방법을 집게 합니다.

내보내기 전, 검증기가 보고서를 원장과 대조합니다.

```bash
node scripts/check-ledger.mjs ledger.md --deliverables report.md
```

원장에 없거나 분석 중 반증된 주장을 인용한 문장이 있으면 결과물을 실패 처리합니다. 통과하지 못한 보고서는 완성이 아닙니다.

## 사용

설치한 뒤에는 평소 말로 물어보면 됩니다. 이런 요청에 스킬이 뜹니다.

- "이 앱 어떻게 돌아가?"
- "구조 그려줘."
- "이 기능, 다시 만들 수 있을 만큼 설명해줘."

에이전트는 REA를 돌리고, 주장 원장을 쓰고, 주장이 확인될 때까지 루프를 돌린 뒤, 검증기를 거쳐 템플릿 형식의 보고서를 돌려줍니다. REA와 분석 엔진(예: 네이티브 바이너리용 Ghidra)이 에이전트에 붙어 있을 때 가장 잘 동작합니다. 없으면 인용할 증거가 적어, 루프의 규칙에 따라 그 부분은 추측으로 채우는 대신 "unknown"으로 남습니다.
